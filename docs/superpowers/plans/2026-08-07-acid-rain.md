## Risks

- Bukkit `Material.isAir()` initializes registry in unit tests. Avoided by direct air-material checks.
- Java 25 was required by the existing build. Verification was run with `JAVA_HOME=C:\Program Files\Java\jdk-25.0.3`.
- Existing full suite depended on `build/run-server/plugins/BetterModel/models` files that were not produced by clean builds. A minimal verification task now copies packaged BetterModel sources there before tests.
- Environmental erosion can be dangerous. The policy is whitelist-first with hard safety barriers.

## Success Criteria

- Acid Rain starts/stops/reloads and reports info.
- Config invalidity fails toward safe behavior.
- Damage requires active storm, affected world, online player, exposure, no bypass, incomplete protection, and elapsed interval.
- Protection clamps to 0-100 percent.
- Erosion is limited by whitelist, event cap, and per-second cap.
- Leaves never erode even if whitelisted.
- Ores, containers, crops, dirt/grass, and special blocks are not eroded by default.
- Runtime cleanup removes tasks, presentation, caches, temporary state, and weather snapshots.
- `test` and `clean build` pass.

### Configuration

Added `modules.acid-rain.enabled` and full `acid-rain` defaults for worlds, duration, warning, automatic activation, damage, levels, escalation, protective items, environment erosion, water, bossbar, actionbar, sounds, and particles.

Environment erosion now includes `environment.destruction.vertical-scan-depth`. Candidate harvesting checks a bounded vertical range from the local surface and player height so whitelisted stone/cobblestone/deepslate/logs/planks can be found in normal terrain and structures while still respecting every block safety barrier.

The current visible-event defaults are `radius: 18`, `max-blocks-per-event: 3000`, `max-blocks-per-second: 90`, `candidates-per-cycle: 90`, and `vertical-scan-depth: 16`. Planks were added to the whitelist because the manual test structure used `OAK_PLANKS`, which the earlier safe whitelist did not permit.

### Limitations

- Water contamination is configured and reserved, but block-level water mutation is intentionally off by default and not implemented as ocean/world conversion.
- Custom items, custom sounds, custom particles, mobs, bosses, loot, and resource-pack assets are extension points only.
- The runtime uses vanilla weather as presentation during the Acid Rain event, but Acid Rain state is owned by the module and does not depend on `world.hasStorm()`.

### Decisions

- Respected the repository stack: Paper API 26.2 alpha, Java 25, Gradle Groovy DSL.
- Registered Acid Rain after Nexus so erosion can respect Nexus protected containers.
- Used a cancelable custom erosion event to allow future external protection plugins to veto block changes.
- Kept dangerous config invalidity fail-safe: no damage, no destruction, no automatic starts.
- Used pure domain tests instead of Mockito or live server startup.
- Made bypass non-inherited after runtime testing showed admin/OP players could be immune while reporting 0 percent equipment protection.

## Follow-up Completion Report (2026-08-14)

### Acid Rain intensity and safety hardening

- Per-level destruction tuning under `levels.<level>.destruction`
  (`interval-ticks`, `candidates-per-cycle`) with defaults ACID 40/30,
  TOXIC 20/60, CHEMICAL 10/90. The environment task now runs on a 10-tick
  cadence and the runtime gates cycles on the active level's interval, so the
  three levels are genuinely different (roughly 15/60/90 blocks per second).
- `max-blocks-per-second` is now a real per-second budget shared across cycles
  (keyed by wall-clock second), and `max-blocks-per-event` still caps the whole
  event. Higher levels never exceed the safety caps and never bypass the
  whitelist.
- Erosion candidates carry their harvest origin + radius and the environment
  service re-checks the radius at processing time; out-of-radius candidates are
  skipped. The service also rejects any non-ACTIVE storm, so WARNING/ENDING/
  INACTIVE can never mutate blocks even if the runtime gating regressed.
- WARNING now shows particles (same system as ACTIVE), messages, sounds and
  bossbar, without any destruction.
- Config hardening: NaN/Infinity damage/contamination/protection rejected;
  absurd destruction values clamped with warnings (radius 64, candidates 512,
  per-second 120, per-event 10000, scan depth 128); sound volume/pitch clamped;
  environment queue capped at 4096 and de-duplicated.

### Items and gunpowder crafting

- New catalog items `potassium_nitrate` (Nitrato de Potasio, base SUGAR, model
  data 1009) and `nitric_acid` (Ácido Nítrico, base POTION, model data 1011),
  mechanic `catalog-material`, seeded from the JAR, validated by the catalog
  validator, wired into Java + Bedrock packs (models, shared textures,
  `item_texture.json`, lang es/en). Ácido Nítrico is documented as prepared for
  future mechanics and is not wired into any gameplay system yet.
- `CustomItemRegistry` now resolves catalog-only items through
  `findById`/`getAllItems`, so `/bigcasares give potassium_nitrate` and tab
  completion work without a dedicated mechanic module.
- Recipe system extended: custom-item ingredients
  (`bigcasares:potassium_nitrate`) become real `RecipeChoice.ExactChoice`
  stacks (no vanilla substitution), vanilla material choices support
  `COAL|CHARCOAL`, and `result-material: GUNPOWDER` produces a vanilla result.
  The gunpowder recipe is a real Bukkit shapeless recipe registered atomically
  by `CatalogRecipeRuntime` on enable and on `/bigcasares reload items`.
