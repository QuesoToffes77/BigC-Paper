# Jeremy Implementation Plan

## Objective

Implement the Jeremy global hunter in BigCasares using the existing module lifecycle, safe configuration, PDC identity, real-time persistence, pure domain tests, and one owned runtime task.

## Tasks

1. Inspect module, scheduler, entity, command, configuration, persistence, and test conventions.
2. Write RED tests for lifecycle, target selection, power, damage, Golden Helmet, stuck detection, Ultrasound, persistence, and assets.
3. Implement pure domain policies and make targeted tests GREEN.
4. Implement Bukkit storage, spawn, power reading, pathfinding orchestration, combat, Ultrasound, and celebration.
5. Register configuration, command, permissions, listener, scheduler, and module lifecycle.
6. Exclude Jeremy from random MobScaling mutations through its shared PDC identity.
7. Run all tests and a clean build without skipped tests.
8. Deploy to the local Paper server and verify startup, command state, persistent cooldown, and measured baby-zombie speed.

## Risks And Controls

- Duplicate Jeremy: the global cycle accepts a start only from `RESTING`.
- Restart timing drift: epoch-millisecond phase deadlines are persisted atomically.
- Target switching: runtime restores the fixed UUID target.
- Camping: progress-based stuck detection gates a charged, rate-limited ray.
- Unfair wall damage: ray traversal allows at most two unique solid blocks.
- New-player one-shot: configurable raw melee damage is clamped to 4-11 HP.
- Chunk pressure: spawn and reposition inspect loaded chunks only.
- Reload residue: stable PDC identity plus stale-entity reconciliation and owned cleanup.
